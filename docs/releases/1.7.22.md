# 1.7.22

## 变化

### 修 `0.2.2-rc.5` 桌面端「应用」卡死：运行时搬到了用户目录

- rc.5 的官方安装器把打包运行时从 `resources\runtime\primary-runtime` 搬到了用户数据目录：`<DSH_HOME>\dsh-runtimes\dsh-primary-runtime\dependencies\pnpm\bin\pnpm.mjs`，并留下一个空的 `resources\runtime`。
- 旧代码只认安装目录，于是解包后建 `app/runtime` 链接必定失败：`runtime link: missing_runtime` → 「应用」中止并**保留原归档**。表现是补丁已经写进 `resources\app`，但 `app.asar` 还在、Electron 仍从归档加载，等于没生效。
- 现在 `findPnpmEntry` / `ensureAppRuntimeLink` 会先看安装目录，找不到再扫 `<DSH_HOME>\dsh-runtimes\*`（`dsh-primary-runtime` 优先），并支持"root 本身就是 primary runtime"的布局（入口路径 `dependencies/pnpm/bin/pnpm.mjs`）。
- 已存在的安装容器链接（`app/runtime` → `resources\runtime`）会被**备份后改指**到已验证的运行时根，报 `migration: runtime_container`；指向任何其它位置的活链接照旧保留并报 `runtime_conflict`。
- `missing_runtime` 的错误文案现在会同时给出用户数据目录，避免再次让人猜运行时去哪了。

### 修 `#35` 在已应用宿主上必然误报漂移

- `#14 ESCALATION_GRANT_UNCONDITIONAL` 会把整个 `approveEscalation` 函数体换成 `return mode`，`switch (outcome)` 随之消失，`#35` 的锚点就永远不可能再命中——每次 apply 之后都必定报一条假漂移。
- 两条补丁意图完全重叠（升级结果不再抛），因此 `#35` 改为 `markersAny` 并接受 `#14` 的落地标记：`#14` 已应用即视为 `#35` 达成。

## 升级后要做的

1. 状态页点「应用」。若之前卡在 `missing_runtime`，这一版会自动找到用户目录里的运行时并完成链接与换包。
2. 退出并重新打开 DSH，确认 `resources\app.asar` 已改名成 `app.asar.purge-*.bak`。
3. 自检：宿主补丁应为 75/75 applied、0 漂移。

## 已知限制

- 桌面壳 6 条（`#45 #46 #82 #83 #84 #92`）本次在真实 `0.2.2-rc.5` 安装上**已复测通过**（`patchDrift` 零漂移），但 Windows 之外未单独回归。
- CLI 侧自检会出现 1 层 `unknown`：权限/沙箱策略在应用外无法观测，提示语本身要求「请在运行中的面板重测」，不是故障。
- 「用官方安装器更新 DSH」仍依赖 `wscript` 执行 `.jsw`，部分安全软件（如火绒）会拦截该动作；被拦时按 README 用官方安装包手动升级。
